# ADR-001: Cookie-Based JWT аутентификация с ин-токен CSRF и версионированием сессий

Status: Accepted

## Context
В веб-приложениях типа SPA/PWA хранение JWT в `localStorage` или передача через заголовок `Authorization: Bearer` создает уязвимость перед XSS-атаками: любой вредоносный скрипт может прочитать токен и отправить его третьей стороне. Кроме того, классические stateless JWT невозможно отозвать до истечения их срока жизни без ведения черных списков в оперативной памяти (Redis), что усложняет инфраструктуру на серверах с 1 GB RAM. При этом использование обычных cookies открывает приложение для атак подделки межсайтовых запросов (CSRF).

## Decision
1. Хранить токены исключительно в cookies с атрибутом `HttpOnly`:
   - `access_token` (JWT HS256, срок жизни 15 минут).
   - `refresh_token` (JWT HS256, срок жизни 30 дней).
2. Защита от CSRF реализована через встроенный токен:
   - При выпуске access-токена генерируется случайная 16-байтная hex-строка, которая вшивается в claims самого токена (`csrf: "<hex>"`).
   - Клиенту эта строка отдается в доступной JS cookie `csrf_token` и заголовке ответа `X-CSRF-Token`.
   - Middleware `CSRF` для всех мутирующих запросов (`POST`, `PUT`, `PATCH`, `DELETE`) требует заголовок `X-CSRF-Token` и сверяет его со значением из claims проверенного access-токена.
3. Инвалидация сессий реализована через поле `token_version` в таблице `users`:
   - При смене пароля или выходе со всех устройств поле инкрементируется (`token_version = token_version + 1`).
   - При вызове `/auth/refresh` сервер проверяет соответствие `claims.TokenVersion == user.TokenVersion`. При несовпадении сессия немедленно прекращается.

## Reason
- **Абсолютная защита от кражи токенов через XSS:** JavaScript в браузере не имеет доступа к телу JWT токенов.
- **Надежная защита от CSRF без состояния:** Серверу не требуется хранить CSRF-токены в сессионном хранилище; проверка выполняется криптографически путем сопоставления заголовка запроса с полезной нагрузкой подписанного JWT.
- **Мгновенный отзыв всех сессий:** Позволяет моментально завершить сессии на всех устройствах пользователя при смене пароля простым инкрементом одного поля в таблице `users`, не требуя развертывания Redis.

## Consequences
- Все fetch-запросы на клиенте обязаны использовать опцию `credentials: 'include'`.
- Мутирующие запросы обязаны передавать заголовок `X-CSRF-Token`.
- Клиентский код в `api/client.js` содержит перехватчик `401 Unauthorized` для прозрачного вызова `/auth/refresh` и повтора исходного запроса.

## Alternatives
- **Токены в localStorage:** Отвергнуто из-за высокого риска компрометации сессий при XSS.
- **Хранение сессий в Redis:** Отвергнуто для минимизации инфраструктурных затрат и потребления памяти (стенд 1 vCPU / 1 GB RAM).
