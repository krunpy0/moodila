# ADR-004: Двухуровневая модель приватности записей с изоляцией новых друзей

Status: Accepted

## Context
В социальных приложениях для ведения персонального дневника пользователям необходим гибкий контроль аудитории:
1. Запись может быть абсолютно приватной (личной), видимой только автору.
2. Пользователь может не хотеть делиться своими обычными записями с определенными друзьями по умолчанию (например, коллегами или малознакомыми людьми).
3. Пользователь должен иметь возможность точечно открыть определенную запись другу, от которого записи обычно скрыты, или наоборот — скрыть конкретный пост от близкого друга.
4. **Критическая уязвимость:** Если пользователь добавляет нового друга, этот друг не должен задним числом получить доступ к интимным записям с кастомной видимостью, созданным до установления дружбы.

## Decision
1. **Двухуровневая схема данных (миграция 0015):**
   - Уровень аккаунта: таблица `user_friend_visibility` (`user_id`, `friend_id`, `hide_by_default`).
   - Уровень конкретной записи: таблица `entry_friend_visibility` (`entry_id`, `friend_id`, `is_hidden`).
2. **Канонический предикат видимости:**
   ```sql
   (e.user_id = $viewer_id)
   OR (
       f.status = 'accepted'
       AND e.is_hidden = false
       AND COALESCE(efv.is_hidden, ufv.hide_by_default, false) = false
   )
   ```
   Постовой оверрайд (`efv.is_hidden`) имеет абсолютный приоритет над аккаунт-дефолтом (`ufv.hide_by_default`).
3. **Изоляция кастомных записей от новых друзей (коммит 49cf20e, миграция 0019):**
   - При принятии дружбы (`friends.Respond` со статусом `accepted`) в БД автоматически вставляются записи со значением `is_hidden = true` в `entry_friend_visibility` для всех существующих постов с кастомной видимостью обоих пользователей.
4. **Каскадная очистка при удалении дружбы (`friends.Delete`):**
   - Немедленное удаление всех записей из `user_friend_visibility` и `entry_friend_visibility` между бывшими друзьями для предотвращения накопления мусорных связей.
5. **Инвалидация кэша:**
   - Изменение настроек приватности вызывает `SummaryCache.InvalidateUser(authorID)`, очищая кешированные месячные сводки.

## Reason
- **Полный контроль над конфиденциальностью:** Пользователь получает гранулярное управление без необходимости создавать закрытые группы или множественные аккаунты.
- **Отсутствие ретроспективных утечек данных:** Новый друг гарантированно не увидит посты, которыми автор делился узким кругом до их знакомства.
- **Единый предикат:** Одно и то же логическое правило используется в календаре, ленте, профиле и сервисе уведомлений, исключая рассинхронизацию доступа.

## Consequences
- Любой запрос к записям дневника обязан соединяться с таблицами видимости через `LEFT JOIN`.
- Принятие дружбы выполняет дополнительную операцию `INSERT` для защиты кастомных записей.

## Alternatives
- **Единый булев флаг `is_friends_only`:** Отвергнуто как недостаточно гибкое решение, не покрывающее потребности пользователей в выборочном шеринге.
