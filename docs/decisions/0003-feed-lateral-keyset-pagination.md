# ADR-003: Оптимизация социальной ленты через CROSS JOIN LATERAL и Keyset Cursor

Status: Accepted

## Context
В ранних версиях запрос социальной ленты (`/feed`) строился через объединение таблиц друзей и записей:
`SELECT e.* FROM entries e JOIN friendships f ON ... ORDER BY e.date DESC LIMIT 10 OFFSET 20`.
При масштабировании нагрузочного датасета (20 000 пользователей, 300 000+ записей, степенной граф друзей) производительность ленты катастрофически упала:
- Время выполнения запроса возросло до 1300–1800 мс под нагрузкой.
- Планировщик PostgreSQL выполнял полное сканирование (`Seq Scan`) сотен тысяч строк и выполнял сортировку на диске (`Sort Method: external merge Disk`).
- Пагинация через `OFFSET` приводила к линейной деградации по мере прокрутки ленты пользователем.

## Decision
1. **Курсорная пагинация (Keyset Cursor):**
   - Отказаться от `OFFSET` в пользу строгого сравнения кортежей:
     `(e.date, e.created_at, e.id) < ($cursorDate, $cursorCreatedAt, $cursorID)`
   - Использовать Base64-кодированный курсор: `base64(date|created_at_RFC3339Nano|id)`.
2. **Архитектура запроса через `CROSS JOIN LATERAL`:**
   - Выделить список авторов в CTE `authors` (через индексированный `UNION ALL` по `friendships`).
   - Для каждого автора выполнять независимую выборку ровно `limit + 1` самых свежих записей с проверкой приватности через `CROSS JOIN LATERAL`.
   - Применить внешний `LIMIT limit + 1` ко всему результату.
3. **Специализированные индексы:**
   - Добавить составной индекс `idx_entries_user_date` на `entries (user_id, date DESC, created_at DESC, id DESC)` (миграция 0020).
   - Добавить `friendships_requester_status_idx`, `friendships_addressee_status_idx` и `idx_user_friend_visibility_friend`.
4. **Вынос реакций из основного запроса:**
   - Подсчет лайков и реакций перенесен во второй пакетный запрос `SELECT ... FROM likes WHERE entry_id = ANY($1::uuid[])` с агрегацией в памяти Go.
5. **Верификация эквивалентности:**
   - Написана CLI-утилита `backend/cmd/verify_feed/main.go`, проверившая 100% идентичность результатов между старым и новым запросами на выборке из 200 пользователей и до 1000 записей на пользователя.

## Reason
- **Устранение деградации от объема данных:** Запрос перестал зависеть от общего размера таблицы `entries`. Планировщик выполняет быстрые `Index Scan Backward` по локальному индексу каждого автора.
- **Взрывной рост скорости:** Задержка ответа ленты под нагрузкой сократилась с ~1300 мс до ~7.5 мс на датасете из 300 000 записей.
- **Устранение диск-сортировки:** Все сортировки выполняются по существующим B-Tree индексам с нулевым потреблением дискового ввода-вывода.

## Consequences
- Нельзя выполнять переход к произвольной странице N (только последовательный бесконечный скролл «вперед»).
- Изменение структуры индекса `idx_entries_user_date` сломает план выполнения запроса.

## Alternatives
- **Fan-out on write (Inbox-таблицы ленты для каждого пользователя):** Отвергнуто, так как дублирование записей для сотен друзей при создании каждого поста создавало бы огромный объем дисковых операций записи и требовало бы сложной синхронизации при изменении приватности записей.
- **Материализованные представления (Materialized Views):** Отвергнуто из-за невозможности обеспечения real-time актуальности и накладных расходов на их обновление.
