# ADR-002: Использование чистого SQL через pgxpool вместо ORM

Status: Accepted

## Context
Moodila разрабатывается для работы в условиях ограниченных серверных ресурсов (стенд 1 vCPU / 1 GB RAM) и рассчитана на обработку до 200–300 req/s при десятках тысяч пользователей и сотнях тысяч записей. Основные запросы приложения (социальная лента, двухуровневая приватность, аналитика тегов, инсайты) требуют сложных реляционных конструкций (`CROSS JOIN LATERAL`, `UNNEST`, CTE, оконные функции, кортежные сравнения). Использование тяжелых ORM (таких как GORM) накладывает заметные накладные расходы на рефлексию, выделение памяти и усложняет тонкую оптимизацию планов выполнения. Кроме того, при работе с облачными провайдерами PostgreSQL (например, Supabase через PgBouncer в режиме transaction pooling) использование подготовленных выражений (Prepared Statements) приводит к ошибкам.

## Decision
1. Полностью отказаться от ORM в пользу чистого параметризованного SQL на базе драйвера `jackc/pgx/v5` и пула соединений `pgxpool.Pool`.
2. Настроить выполнение запросов в режиме простого протокола:
   `cfg.ConnConfig.DefaultQueryExecMode = pgx.QueryExecModeSimpleProtocol`.
3. Сосредоточить всю работу с БД в слое `internal/repository/`, исключив SQL из хендлеров.
4. Управлять схемой БД через последовательные нумерованные SQL-миграции (`migrations/0001_...sql` по `0020_...sql`), встроенные в бинарник через `embed.FS`.

## Reason
- **Максимальная производительность и минимальное потребление RAM:** Отсутствие оверхеда на рефлексию Go и генерацию абстрактных SQL-запросов.
- **Полный контроль над запросами:** Возможность вручную проектировать сложные запросы (например, lateral join для ленты) и индексы под них, гарантируя использование `Index Scan` вместо `Seq Scan`.
- **Совместимость с PgBouncer / Supabase:** Режим `SimpleProtocol` предотвращает сбои "prepared statement does not exist" при пулинге транзакций.
- **Атомарные миграции:** Возможность выполнять многострочные DDL-скрипты в одной транзакции без внешних зависимостей типа Goose или Flyway.

## Consequences
- Разработчикам необходимо вручную маппить строки результатов (`rows.Scan`) в структуры Go.
- Необходимость дисциплинированного написания параметризованных запросов (`$1, $2, ...`) для предотвращения SQL-инъекций.
- Изменения схемы требуют аккуратного написания DDL-миграций вручную.

## Alternatives
- **GORM:** Отвергнуто из-за высокого потребления CPU/памяти при сериализации больших выборок и плохой поддержки сложных конструкций PostgreSQL (`LATERAL`, `UNNEST`).
- **Ent / SQLBoiler:** Отвергнуто из-за избыточной кодогенерации и усложнения процесса сборки.
