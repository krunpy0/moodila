# Предпочтение поддержки и комментарии

Источник: миграция `0024_entry_support_preference.sql`, `backend/internal/{models,handlers,repository}/entries.go`, `repository/feed.go`, `frontend/src/pages/{AddEntry,Calendar,Feed}.jsx`.

`entries.support_preference` — строка с ограничением CHECK и значением по умолчанию `''`:

| Значение | Смысл |
|---|---|
| `''` | Предпочтение не указано |
| `listen` | Хочется, чтобы выслушали |
| `advice` | Нужен совет |
| `reach_out` | Просьба связаться |
| `no_discussion` | Без обсуждения, новые комментарии закрыты |

Поле передаётся через `POST /entries` вместе с записью. Отсутствующее поле сохраняет прежнее значение при обновлении; пустая строка явно сбрасывает выбор. Новая запись без поля получает `''`. Недопустимые значения отклоняет HTTP-валидация и ограничение БД.

Предпочтение показывается в календаре и ленте через `SupportPreferenceNote.jsx`, не меняет аудиторию записи и не отправляет отдельный запрос на помощь. `listen`, `advice`, `reach_out` — пояснения, без запрета комментариев.

При `no_discussion` UI закрывает ввод комментариев. Репозиторий `Feed.AddComment` дополнительно блокирует создание внутри транзакции с `SELECT ... FOR UPDATE`; HTTP-ответ — `403` с `code: "comments_closed"`. Существующие комментарии остаются доступными, реакции сохраняются. Проверку доступа к записи нужно сохранять независимо от предпочтения.

Проверки: `TestValidateSupportPreference` в handlers; `TestSupportPreferenceIntegration` в repository (отдельная БД через `TEST_DATABASE_URL`, тест применяет миграции и удаляет созданных пользователей).
