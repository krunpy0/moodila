# Moodila: проверка активных CCU

## Запуск на своём компьютере

Нужен **Docker Desktop с запущенным Linux Engine**. Устанавливать k6 отдельно,
указывать BaseUrl или переносить manifest не нужно. Скрипт сам поднимет приложение,
подготовит отдельную тестовую БД и запустит k6 в Docker.

Открой PowerShell в `F:\moodila` и выполни:

```powershell
.\loadtest\run.ps1
```

По умолчанию общий бюджет API и PostgreSQL — **1 vCPU и 1 ГиБ RAM**:
одно общее логическое ядро, 512 МиБ для API и 512 МиБ для БД. k6 получает остальные ядра и отдельно
1 ГБ RAM. Генератор не делит выбранное ядро с API/БД. Docker должен видеть
хотя бы два CPU и иметь достаточно памяти для трёх контейнеров и самой VM.
Это измеряет ёмкость ограниченного локального стенда; модель CPU, общий диск,
память хоста, SMT и Docker Desktop могут отличаться от будущего VPS.

Без флагов запускается **подробный тест**: 25, 50, 100, 200, 400 и 800 CCU,
два замера по 5 минут с минутным прогревом на каждый уровень и уточнением границы.
Одна ступень занимает около 12 минут нагрузки, весь поиск может занять больше часа.

**Быстрый тест** запускается отдельным флагом:

```powershell
.\loadtest\run.ps1 -Quick
```

Это предварительная оценка: 50, 200 и 800 CCU,
по одному замеру 30 секунд без уточнения границы. С прогревом это примерно
3–5 минут нагрузки, если все три уровня запустятся. Перед каждой ступенью
печатаются её CCU и длительность. При первом провале/недостоверном результате
тест останавливается. Короткий замер не доказывает длительную устойчивость.

Первый запуск скачивает образы, собирает backend и создаёт 1,36 млн записей —
подготовка может занять ещё несколько минут. Последующие быстрые запуски
переиспользуют данные, если совпадают образы, хеш сидера и число строк.
Сначала можно проверить только работоспособность:

```powershell
.\loadtest\run.ps1 -Smoke -Steps 4 -WarmupSeconds 5 -MeasureSeconds 15 -ThinkSeconds 0.2
```

Smoke проверяет работоспособность, поэтому намеренно не выдаёт предел CCU
(`invalid`, код 1). Для длительного подтверждения выбранного уровня:

```powershell
.\loadtest\run.ps1 -Steps 200
```

Это два замера по 5 минут с минутным прогревом каждый — около 12 минут нагрузки.
Полный подробный поиск всех уровней: `.\loadtest\run.ps1` (может занять больше часа).

Результат: `loadtest/results/<дата-время>/capacity.json`.
`maxEstimatedCCU` — предварительная оценка быстрого режима,
`maxVerifiedCCU` — подтверждённое число активных сессий в подробном режиме без `-Quick`,
`firstFailedCCU` — ближайший проверенный проваленный уровень.

Общие лимиты меняются параметрами `-Cpus` (целое число vCPU) и `-Ram`:

```powershell
.\loadtest\run.ps1 -Cpus 2 -Ram 2g
.\loadtest\run.ps1 -Quick -Cpus 1 -Ram 1g
```

CPU выбираются автоматически: первые `Cpus` ядер для API/БД, остальные для k6.
Docker должен видеть хотя бы `Cpus + 1` CPU. API и БД делят выбранные ядра;
их суммарная доступная вычислительная мощность ограничена выбранным набором CPU.
Память по умолчанию делится поровну, дополнительный swap отключён.
Это бюджет двух контейнеров: память ОС и k6 в него не входит.

При необходимости можно выбрать конкретные CPU и распределить RAM вручную:

```powershell
.\loadtest\run.ps1 -Cpus 2 -Cpuset '0,2' -Ram 2g -ApiMem 768m
```

Оставшаяся память (в примере 1280 МиБ) выделяется БД. При указании обоих
`-ApiMem` и `-DbMem` их сумма не должна превышать `-Ram`.
Фактические лимиты проверяются через `docker inspect` и записываются в `stand.json`.

Подробный режим и `-PrepareStand` заново готовят тестовые данные. Контейнеры API/БД
остаются работать после теста. Остановить их:

```powershell
docker compose -f docker-compose.loadtest.yml down
```

Далее — подробности методики и необязательный запуск на удалённом стенде.

CCU здесь — число одновременно работающих авторизованных API-сессий. Один k6 VU
использует один уникальный аккаунт, выполняет действие и ждёт случайную паузу
от 0,5 до 1,5 `THINK_SECONDS`. По умолчанию средняя пауза — 7 секунд **после**
завершения действия. Длительность ответа входит в длительность пользовательского цикла.

Результат относится к этой модели, данным, настройкам и машине. Это не число
зарегистрированных пользователей, не количество простаивающих вкладок и не
универсальный предел приложения. Браузерный рендеринг, статика, загрузка медиа,
S3 и реальные push-получатели не входят в нагрузку.
Кеш React Query/Service Worker не воспроизводится: каждое действие отправляет
описанные запросы. Доли действий и паузы синтетические; для прогноза реального
онлайна их нужно откалибровать по обезличенной частоте запросов пользователей.

## Модель действий и критерии

За цикл из 20 действий: лента 35%, календарь 20%, следующая страница ленты 10%,
статистика 10%, уведомления 10%, профиль 5%, поиск дневника 5%, запись 5%.
Календарь делает запросы сводки и записей месяца, статистика — `summary` и `series`; пагинация при необходимости
сначала открывает первую страницу. Доли относятся к **действиям**, а не HTTP RPS.
Профиль и календарь проверяются по актуальным форматам API. HTTP 200 с неверным
JSON считается ошибкой. Запись обновляет существующий день бота, не увеличивая
объём записей и уведомлений о новых публикациях.

Каждая ступень — отдельный процесс k6 `constant-vus`: прогрев, затем полный замер.
Ступени и повторы не перекрываются. Авторизация распределяется по первой половине
прогрева; cookie jar сохраняется между итерациями; каждые 10 минут обновляется сессия.
Ошибки подготовки запрещают засчитывать ступень. При больших CCU увеличивайте
прогрев, если все аккаунты не успевают войти: незавершённая авторизация даёт `invalid`,
а не доказательство предела обычных авторизованных сессий.

Для `passed` в режиме длительного подтверждения требуется:

- Полный замер от 300 секунд, длительность кратна 60; все уникальные пользователи вошли до его начала и участвовали в нём.
- Каждый VU явно подтверждает достижение конца замера; общая длительность процесса
  сама по себе не подтверждает завершение. Каждый пользователь должен начать хотя бы
  одно действие в каждом окне (минута, в quick — до 60 секунд). При больших паузах
  это требование может дать `invalid`: такой профиль активности этим тестом не подтверждается.
- p95 полного HTTP-вызова (включая соединение) ≤300 мс; ошибок ≤1% для каждой операции.
- Те же критерии для каждой операции в каждой минуте, минимум 5 ответов на такую выборку
  и минимум 20 ответов на операцию за весь замер. Короткие/малые выборки не дают ёмкость.
- p95 пользовательского действия ≤1500 мс и ошибок действий ≤1% в каждой минуте.
- Темп действий в каждой минуте ≥70% от `CCU / (THINK_SECONDS + ACTION_P95_THRESHOLD/1000)`.
  Это отдельное требование к активности: закрытая модель не должна скрывать зависания падением RPS.
- Нет прерванных запросов/действий, пропусков итераций; p99 задержки таймера генератора ≤250 мс.
  Для завершения начатого действия после конца замера предусмотрено до 46 секунд:
  refresh и два последовательных запроса могут занять три таймаута по 15 секунд.
- Генератор использует другие CPU: в локальном режиме это задаётся Docker автоматически.
  Для необязательного удалённого режима `-SeparateGenerator` подтверждает отдельную машину.
  Контролируйте CPU/RAM генератора и сеть;
  задержка таймера обнаруживает часть проблем генератора, но не доказывает отсутствие всех ограничений.

`failed` означает нарушение заданного качества обслуживания. `invalid` означает,
что измерение не позволяет судить о ёмкости. Пороги не прерывают ступень досрочно;
после неё runner останавливает увеличение CCU при первом неуспешном результате.
Если есть успешная и проваленная ступени, runner автоматически проверяет середину
интервала, пока расстояние между границами не станет ≤10 CCU (`-Resolution`).
Недостоверный прогон останавливает поиск без уточнения границы.

Проверенный максимум — последняя ступень, прошедшая **все повторы** (подробный режим: два).
В быстром режиме сохраняются проверки изоляции, корректности, задержек и активности,
но замер составляет 30 секунд, минимальная выборка — 5 ответов на операцию.
Его результат помечается `preliminary`; поле подтверждённого максимума остаётся пустым.
Первая проваленная ступень — наблюдаемая неуспешная нагрузка, а не доказанный
аппаратный предел. Например, 100 CCU прошли, 200 не прошли: runner проверит 150,
затем уточнит интервал следующими прогонами с теми же критериями и повторами.
Итог — проверенная нижняя и наблюдаемая неуспешная верхняя границы. Если прошли все ступени, предел ещё
не найден: подтверждено **не менее** максимальной ступени. `invalid` не задаёт верхнюю границу.

## Дополнительно: подготовить стенд отдельно от запуска

PowerShell 7, Docker Compose. Из корня репозитория:

```powershell
./loadtest/run.ps1 -PrepareStand -Cpus 1 -Ram 1g
```

Поднимаются только тестовые контейнеры. PostgreSQL 17.6 хранится в отдельном named
volume `moodila-loadtest-postgres-v2`; dev-контейнер не останавливается, его данные
не подключаются. Порт БД 55432 доступен только через loopback. Порт API — 8080.
Backend `.env` не загружается: ключи S3, email, push и Google Drive не наследуются,
автобэкап выключен. Тестовые учётные данные никогда не используйте в production.
Не публикуйте этот стенд в открытый интернет: ограничьте API адресом генератора/VPN.

По умолчанию rate limiter выключен для проверки мощности API. Для проверки
поведения с включёнными ограничениями подготовьте стенд с `-DisableRateLimit:$false`.
Общий IP генератора может упереться в лимит входа; тогда увеличьте прогрев.
Режим записывается в manifest и должен соответствовать цели измерения.

API и БД делят выбранный CPU, каждому задан предел RAM без дополнительного swap.
Это воспроизводимое ограничение контейнеров, а не точная копия произвольного VPS:
модель CPU, диск, конкуренция хоста и память ОС влияют на результат.

Подготовка **пересоздаёт данные ботов** внутри `moodila_loadtest`. Сидер отказывается
работать в БД с другим именем или при наличии чужих пользователей. Ошибка SQL
прерывает транзакцию и подготовку; успех дополнительно проверяется по числу строк.
Данные: 20 000 пользователей, 1 363 740 записей, кольцо дружбы с дополнительными
случайными связями, приватность, реакции и комментарии. 20% аккаунтов активные
(201–365 записей), остальные имеют 15 записей. Это синтетический профиль, а не
подтверждённое распределение production. Выбор аккаунтов перемешивается с seed=42.
Повторная подготовка сбрасывает предыдущие изменения; делайте её перед новой кампанией.

Скрипт печатает путь к `stand.json`. При обычном локальном запуске он используется
автоматически; при удалённом его можно скопировать на машину генератора.
Manifest содержит ревизию/признак незакоммиченных изменений, ID образов,
фактические ограничения контейнеров и количество строк. При изменении сервера
создайте новый manifest. Он описывает подготовку, не заменяет проверку адреса сервера.
Контейнеры остаются работать; остановка вручную:

```powershell
docker compose -f docker-compose.loadtest.yml down
```

## Дополнительно: запуск с другой машины

Проверенная версия k6 — **1.4.0**. Node нужен только для тестов самого набора.
На генераторе должна находиться та же версия скриптов.

```powershell
./loadtest/run.ps1 -BaseUrl http://TEST-SERVER:8080 `
  -StandManifest ./stand.json -SeparateGenerator `
  -Steps 25,50,100,200,400,800 -WarmupSeconds 60 `
  -MeasureSeconds 300 -ThinkSeconds 7 -Repeats 2
```

Результаты находятся в уникальном `loadtest/results/<UTC>/`: один JSON на прогон
и `capacity.json` с `maxVerifiedCCU`, `firstFailedCCU`, причинами и ссылками на прогоны.
Рядом с каждым JSON прогона сохраняется читаемый отчёт `<имя>.json.txt`; эти же
таблицы выводятся в терминал. Формат JSON прогона — версия 3; формат manifest остаётся 2.

В отчёте доступны:

- Число пользователей: задано, вошло до замера, участвовало, дошло до конца;
  уникальные участники каждого временного окна.
- HTTP RPS и действий/с, число запросов и действий по операциям и окнам.
- Задержки: средняя, минимум, p50, p90, p95, p99, максимум; число и доля ошибок.
  Для действий также сохраняются задержки по операциям; для запросов — по операциям внутри каждого окна.
- Фактические доли запросов и действий в JSON, чтобы видеть отличие от заданной смеси.
- Причины неуспешных запросов: транспортная ошибка (включая таймаут), HTTP 429,
  остальные 4xx, 5xx, прочие статусы, неверный ответ при HTTP 200.
- p95/p99/максимум задержки таймера генератора и причины `failed`/`invalid`.

RPS считается по ответам, завершившимся **внутри** интервала замера; служебные
health/login/refresh исключены. Запрос, начавшийся на прогреве и завершившийся
внутри интервала, входит в RPS. Ответ после конца интервала в RPS не входит.
Задержки, ошибки и выборки SLO относятся к действиям, **начатым** внутри интервала,
со всеми их запросами до завершения, включая хвост после конца замера. Поэтому
`requests.samples` и `requests.completedInInterval` могут различаться; делить
`samples` на длительность для вычисления RPS нельзя. Окна задержек определяются
началом действия, окна RPS — завершением отдельного запроса.
Количество запросов и действий, завершённых после конца интервала, указано отдельно
в `drainedAfterInterval` и в текстовом отчёте.

Минимум 5/20 образцов — защита от пустой выборки, а не гарантия точности p95/p99
или вероятности ошибок ≤1%. Редкие операции и короткий quick-прогон дают нестабильные
перцентили. Увеличивайте длительность и смотрите число образцов, прежде чем делать
выводы о редких задержках. `passed` означает выполнение эмпирических порогов в
наблюдавшихся прогонах; статистическую гарантию для будущих запросов он не даёт.

`null` означает «не установлено», а не 0 CCU. Ошибка k6/отсутствие отчёта сохраняется
как недостоверный прогон и не превращается в предел сервера. Runner возвращает
ненулевой код при `failed`/`invalid`. JSON не содержит cookie, JWT или setup-сессий.
Исторические summary старого формата удалены: их нельзя сравнивать с новым CCU-тестом.

Проверка локального запуска (настоящую ёмкость не выдаёт):

```powershell
./loadtest/run.ps1 -Smoke -BaseUrl http://localhost:8080 `
  -Steps 4 -WarmupSeconds 5 -MeasureSeconds 15 -ThinkSeconds 0.2
```

Такой прогон намеренно получает `invalid` и код 1: он только проверяет связность
и контракты. Для короткого теста одного сценария можно вызвать k6 напрямую:

```powershell
k6 run loadtest/load-test.js -e SCENARIO=smoke -e CCU=4 `
  -e WARMUP_SECONDS=5 -e MEASURE_SECONDS=15 -e THINK_SECONDS=0.2
```

Прямой k6 может вернуть 0, если HTTP-пороги пройдены, даже при `result.status=invalid`.
Для итоговой оценки используйте runner. Старые `ramp`, RPS-ступени, `AUTH_TOKEN`,
`USERS`, `VUs`, `Duration` и `breakpoint-test.js` удалены; CCU больше не вычисляется из RPS.

Параметры одного k6-прогона: `BASE_URL`, `CCU`, `SCENARIO=ccu|quick|smoke`,
`WARMUP_SECONDS`, `MEASURE_SECONDS`, `THINK_SECONDS`, `TOTAL_SEEDED_USERS`, `SEED`,
`P95_THRESHOLD`, `ACTION_P95_THRESHOLD`, `ERROR_THRESHOLD`, `MIN_SAMPLES`,
`ISOLATED_GENERATOR`, `SEPARATE_GENERATOR`, `REVISION`, `STAND_METADATA`, `REPORT_PATH`.
Реальные параметры входят в JSON; не сравнивайте CCU между разными моделями/SLO.

## Мониторинг и повторяемость

На сервере параллельно сохраняйте `docker stats`, CPU steal, RAM/swap и дисковый I/O.
На генераторе контролируйте CPU/RAM и пропускную способность сети. Для диагностики
SQL доступен `pg_stat_statements` (расширение создаётся сидером). `total_exec_time`
показывает время выполнения, а не чистое потребление CPU. Перезапуск/ошибки API,
неполная подготовка и проблемы генератора требуют повторного измерения.

Подтвердите найденный уровень длинным прогоном, например 1800 секунд с двумя
повторами; это также проверит refresh токенов. Повторите кампанию после подготовки
чистой фикстуры. Для других привычек пользователей меняйте `ThinkSeconds` и
публикуйте результаты раздельно. Для браузеров/медиа нужны отдельные сценарии.

## Проверки самого набора

```powershell
node --test loadtest/*.test.mjs
# Включить короткую интеграционную проверку настоящим k6 на mock HTTP API:
$env:K6 = 'C:/tools/k6.exe'
node --test loadtest/*.test.mjs
```

Mock-проверка не измеряет производительность Moodila. Она проверяет cookie/CSRF,
контракты, фазы метрик и формирование отчёта; отдельные тесты проверяют ошибочные
и прерванные измерения. Бэкендовый `TestPerformanceIntegration` проверяет SQL
и корректность ответов; он не является измерением CCU.
